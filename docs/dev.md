# developing moth

## toolchains

- OCaml 5.5.2 in a local opam switch (`_opam/`), with dune, yojson and alcotest.
- C++20 with cmake (Makefiles generator, no ninja). Native build uses Apple clang. The Windows helper uses mingw-w64 from Homebrew (`x86_64-w64-mingw32-g++` and `i686-w64-mingw32-g++`).
- The window uses Qt 6 from Homebrew's `qtbase` (`brew install qtbase`; 6.12 here), its Core, Gui, Widgets, Network and Test modules only, linked dynamically. `make` finds Qt with `brew --prefix qtbase`; set `QTBASE` to use another install.
- The terminal's screen state comes from libvterm (MIT; `brew install libvterm`), which CMake finds through `pkg-config` (`brew install pkgconf`).
- Nothing needs sudo. `opam init` runs with `--no-setup`, so no shell profile is touched.

## setup

    make setup

This runs `opam init --bare --no-setup`, creates the switch in this directory and installs dune, yojson and alcotest. Creating the switch compiles OCaml and takes several minutes. Every OCaml command goes through `opam exec --`.

## build and test

    make build    # dune build, copies the moth executable to bin/moth
    make test     # native C++ unit tests (build/native), then dune test, then test-app
    make helper   # the Windows helper (x86_64 only) and the stand-in game (64-bit and 32-bit), into bin/
    make app      # the window (build/app), copied to bin/moth-app; and build/app/it_app, for the scenarios in a bottle
    make test-app # the window's tests (build/app), offscreen, through ctest
    make clean

Variables: `WINE` (path to CrossOver's wine) and `MOTH_TEST_BOTTLE` (default `uhmm`), both overridable on the command line.

Build output (`_build/`, `_opam/`, `build/`, `bin/`) is gitignored.

## memory budget

`MOTH_BUDGET_MB` is read once, when the daemon starts. A whole number from 1 to 65536 is the most memory, in MiB, the helper may use to hold a hunt's candidates; every `find` sends it with its scan. Past it, the helper stops tracking groups from the end of the hunt's list (the `untracked` note) and searches them again on the next number. Unset or empty, the helper's own budget holds (1536 MiB). Anything else is ignored, with a line in `core.log`. A running daemon keeps the value it started with: `moth stop` first, then run the next command with the new value.

`MOTH_SNAPSHOT_MB` is read the same way, once, when the daemon starts: a whole number from 1 to 1048576 is the most memory, in MiB, that a `snapshot` may take. The default is 8192. A snapshot costs as much memory as the game's writable memory, held by the helper until the hunt has narrowed: it is released once every group is at or under 64,000,000 places and its values fit the budget. While a snapshot hunt narrows, the helper can briefly hold about the snapshot plus twice the budget. A snapshot hunt follows aligned values in six forms: 4-byte and 8-byte whole numbers and decimals, 2-byte whole numbers, and 1-byte whole numbers in the wider tier. A value at an odd address is found by typing its number, not by how it moves. Above about 5.3 GiB of writable memory, the 1-byte form is not followed by change at the default budget. Apart from snapshots, a scan with very many matches (a dense scan) can briefly run about 2 to 3.5 GiB over the budget while it stores their values. Anything else in `MOTH_SNAPSHOT_MB` is ignored, with a line in `core.log`.

## kept values

`moth kept --json` gives each kept value's `set_to` and `put_back`. `set_to` is what the value's newest write wrote, shown as the value shows numbers, or null when there is none. Its newest write is the newest that `undo` can still reverse at its address and as its value type, made by row or by name, before or after `keep`. `put_back` is true when the value reads as it did before that write: the bytes there now are the ones the write replaced, not the ones it wrote (never when it can't be read). The text form says `you set it to <set_to>; it is back to what it was before.` after the value's line. Neither says why; the game working the value out again and ordinary play look the same.

## row writes

`set <#n> <number>` and `keep <#n> [name]` take row n from the last recorded `results` listing (`--near` included), until the hunt changes. With `--at <0xaddr>` they don't: row n is looked up afresh in the current hunt, numbered as a plain `results` numbers it (fewest matches first, `--all` as given on the write, never `--near`), and the remembered listing is neither read nor changed. No row n: `no result #n. run: moth results`. A row n whose address is not the one given, or, with `--kind <interp_id>` (the row's `interp_id` in `results --json`), whose interpretation is another: `row <n> is not at <0xaddr> any more: the list changed. look again: moth results`, and nothing is written or kept. On `set` and `keep`, `--kind` and `--all` go only with `--at` (`--kind goes with --at`, `--all goes with --at`). The window writes this way: a row it shows is written or kept with its address, its `interp_id`, and `--all` while the rarer forms are shown, so another client listing in between never moves it, and its own polls never move another client's row numbers.

A write by row answers with the row's address after its number: `set #1 (0x6c55dfb8) to 98 (was 97)`, `kept #2 (0x6c55dfb8) as xp (42, whole number)`, and so does the event's `summary`; a client can check where it wrote. A write or keep by name or by address keeps its text (`set xp to 95 (was 60)`, `kept 0x10 as hp (...)`). `undo` still says `restored #1 to 97`.

## who is speaking, and whether it acted

The `moth` command reads `MOTH_ACTOR` once, for every command that sends a request (bare `moth`, `help` and `daemon` never read it): `agent` sends actor `agent` with every request, `user`, unset or empty sends `user`, anything else exits 2 with `MOTH_ACTOR must be user or agent` (`Client.actor_of_env`). The actor is in the request's `busy` line and in its event. Every event has `act`, a boolean: true unless the command is one of the reads (`bottles`, `ps`, `status`, `results`, `kept`, `log`, `games`); also true when a read let go of the game or the helper (the recorded-anyway exception below). `status --json` has `"proto": 2` (`Daemon.protocol`) in all four of its answers (not attached, attached with no hunt, attached with a hunt, just closed); a service that answers no `proto` is protocol 1. `Client.watch ?started ?idle`: `started` is called once with the `seq` of the reply before any line, and `idle` whenever half a second passes with no line, ending the watch with `Ok ()` when it returns false. `moth watch` that is dropped watches again from `--after` when one was given, else from the `seq` the first reply gave, until an event it printed replaces it.

`quiet [on|off]` is recorded. It is kept in the daemon and in `$MOTH_HOME/quiet` (present means on), so a restart of the service keeps it, and `status --json` has `"quiet"` beside `"proto"` in all four answers. `on` answers `quiet: the agent is not told what you do. it can still look: moth log`, `off` answers `the agent is told what you do again`, no argument says `quiet is on` or `quiet is off`, anything else is `quiet takes on or off`. `Client.call ?record:false` sends an unrecorded read.

`moth wait --session <dir>` (not in `moth help`, not a request, and it does not read `MOTH_ACTOR`) is run by the agent's `Stop` hook. Exit 2 means it printed a note and nothing else does: a usage error or an unexpected failure prints one line and exits 1, and every other end is exit 0 with nothing printed. The last component of `<dir>` is the process id of the agent session: decimal digits, above 0 (anything else counts as not alive). When that process is not alive (`kill pid 0` fails other than with EPERM) or `<dir>` is gone it exits 0, at its start and on every idle tick, every feed line and every pause of its retry loop. It reads nothing from stdin, writes its pid to `<dir>/waiter` (through a temporary name carrying its own pid) and exits 0 when it reads another pid there (a newer waiter took over). Once the watch is up it reads `status --json`, unrecorded and as actor `user`, for `proto` (not `Daemon.protocol`: exit 0) and `quiet`; a game that read finds closed is recorded and reaches it on the feed. Every socket read waits at most 30 seconds (`MOTH_WAIT_TIMEOUT`, in seconds, for tests): a service that stays silent is treated as not answering. With no service answering, or after the feed drops, it tries again every second from its cursor, looking at the session, the waiter file and what it holds every quarter second, so a `moth stop` it was told of at the end of the feed is still told. `<dir>/cursor` is the seq and, when moth was quiet at it, ` quiet` (`123 quiet`); a waiter that finds one starts from it, quiet state included, and replays the feed after it; with none, it starts from the `seq` the watch reply gave and writes it at once. `Wait` (no sockets, files or clock; `moth wait` gives it the time) bundles what the person did: an event counts when its `seq` is above the cursor, its actor is not `agent`, `act` is true and the command is not `quiet`, and moth is not quiet (a successful `quiet on` or `quiet off` event, from anyone, sets that; `quiet on` also drops what is held). It tells when something is held, no `busy` line is waiting for its event, and 1.5 seconds have passed since the last line or 10 since the first held event. The note, on stderr with exit 2, is `[moth] the person did this in moth:` and a line `- <cmd args>: <summary>` (`failed: <summary>` for a failure) per event, oldest first; more than 12 and the first line is `- (<n> earlier steps: moth log)` followed by the newest 12. Before exiting 2 it writes the cursor; it writes it while quiet whenever it moves. `moth wait` with no `--session` says `wait is run by the agent's hook: moth wait --session <dir>` and exits 1.

## moth agent

`moth agent` (not a request, and it does not read `MOTH_ACTOR`) starts Claude Code on this moth session. It takes no argument (`agent takes no arguments`, exit 2). It finds the program (`MOTH_CLAUDE` when set, which must be an executable file; else `claude` in a `PATH` folder; none: `claude code is not installed, or not on PATH. moth works without it: use the window, or type moth commands here.`, exit 1, nothing written, no service started), reads `status --json` as the user (this starts the service, as any command does) and refuses a service whose `proto` is not `Daemon.protocol` (`moth's background service is from another build of moth. stop it and it starts again by itself: moth stop`, exit 1). `Agent.prepare` then writes `$MOTH_HOME/agent/<pid>/settings.json` and `instructions.md` (the text it appends to the agent's system prompt, for the person to read; folders 0700, files 0600), makes `$MOTH_HOME/agent/work`, and removes sibling folders named for a process id that is not alive (nothing else under `agent/`). It changes to `agent/work`, sets `MOTH_ACTOR=agent`, `MOTH_HOME` and `PATH` (moth's own folder first) and execs `<claude> --settings <dir>/settings.json --append-system-prompt <instructions> <first prompt>`, so its pid is the session's: `moth wait --session <dir>` in the Stop hook ends when it does. The settings carry the same three variables, the one approval `Bash(moth *)` and the hook `'<moth>' wait --session '<dir>'` (paths in single quotes). Nothing under `~/.claude` or `~/.claude.json` is read or written: the settings go to that one session only. If the program cannot be run, the session folder is removed and the not-installed text is said. Tests point `MOTH_CLAUDE` at a stand-in (`core/integration/stub_agent.ml`, built as `stub_agent.exe`, described under the end-to-end scenarios) and never run the real `claude`.

## the feed, and reads that leave no trace

A client can follow what moth does, whoever asks it. `watch` (opts: `after`, an event number) is answered `{"id":..,"ok":true,"result":{"seq":N},"text":""}`, N being the newest recorded event, and the connection then stays open. Each recorded request sends `{"busy":{"actor":..,"cmd":..,"args":[..]}}` as it starts and `{"event":{..}}` once it ends, the object being the line `events.jsonl` gained. With `after` = k, the stored events after k come first as event lines, oldest first, the newest 1,000 at most. Sixteen watchers at most; the next is answered `too many watchers`. The daemon never waits for a watcher: one whose socket can't take a line at once is closed, and should watch again with `after` set to the newest `seq` it has. A last line without a newline was cut off there; ignore it. The connection also closes when the daemon stops, after the stop's own event. `moth watch [--after <seq>] [--json]` prints the feed, an event as `moth log` does and a start as `working: <cmd> <args> (<actor>)`, watches again by itself if it is dropped, and ends with `moth stopped`.

A request with `"record": false` is answered as usual but takes no event number, adds no line to `events.jsonl` and tells no watcher: for polling. An unrecorded `results` also leaves alone the listing that `set <#n>` and `keep <#n>` without `--at` take their row from; only a recorded `results` (such as `moth results`) replaces it. Only `bottles`, `ps`, `status`, `results`, `kept`, `log` and `games` may ask; any other command is refused, unrecorded, with `only commands that change nothing can go unrecorded`. One exception: a read that makes the daemon let go of the game or of its helper is recorded anyway, so watchers learn why the game went. That is a `status` that finds the game closed, or any read the helper answers with `target_gone` or `helper_lost`. It takes a `seq` and goes into `events.jsonl`, and watchers get its event with no `busy` line before it. The command line never sends `record`; `watch` is never recorded.

## launch and games

`moth launch --bottle <bottle> <full path to game.exe> [args]` starts the program under CrossOver's wine in that bottle and answers at once; it does not wait for the game. The path must be absolute, end in `.exe` (any case) and exist. Everything after the path is the game's own arguments, passed untouched, `-windowed` or `--json` included (the command line stops reading moth's options at the path). The game runs in its own session with stdin from `/dev/null`, so it outlives the daemon; its output is appended to `[home]/launch.log`. Each launch is remembered in `[home]/games.json`, a JSON list of `{"name","bottle","path","last"}`, newest first, one entry per bottle and path, 20 at most; a file that can't be read counts as empty and is replaced by the next launch. `moth games` lists them (`name  bottle  path`; json: a list of `{"name","bottle","path"}`) and may be sent with `record: false`; `launch` may not. A launched game is not attached: once it is up, run the `moth attach` line the answer prints. The daemon takes the starting function as `~launch` (`Daemon.default_launch` is the real one; tests pass a fake), so only the integration scenarios start a real game.

## the window

    make build && make app
    bin/moth-app

`bin/moth-app` is one more client of the background service, like `moth`, and talks to nothing but `[home]/core.sock`. It honours `MOTH_HOME` as `moth` does (made absolute; unset, `~/Library/Application Support/moth`) and `MOTH_BIN`, the `moth` program it runs to start the service (unset, the `moth` next to `moth-app`, so `bin/moth`). The service is started in two cases only. The first is when the window opens, if nothing answers at the socket. The second is when one of the user's own actions (a recorded request) finds no service. Either way the window runs `[MOTH_BIN] status` once with that home and waits for it to end (10 seconds at most); an action is then sent again. If the service still doesn't answer, the line says `moth's background service is not answering. see [home]/core.log`, or, when the `moth` program itself could not be run, `could not run [MOTH_BIN]. set MOTH_BIN to the moth program.` While the window is visible it reads `status` on showing and then once a second, unrecorded. These reads never start the service, so `moth stop` leaves it stopped until the next click. The window follows the feed. When the feed drops, it says `lost moth's background service. trying again…` (or, when the event just before the drop was a `stop`, `moth's background service was stopped. it starts again with your next action.`), keeps that line while polls find nothing, and watches again every second from the newest event it has seen. If the service refuses the feed (`too many watchers`), the line says so in the core's words and the window keeps trying every second. A failed action shows the core's whole error, which the action's event (its first line) does not replace. After each event the window reads `status` again (once more if a read was already out; the read is sent even while the next request runs, and the core answers it when that one is over), and only then do the lists read themselves again. A `moth status` that hangs is given up on after 10 seconds and killed; the window never waits on it.

The user's own requests go one at a time: while one is unanswered, or while the feed says any request is running, a click sends nothing and the line says `moth is busy: <its words>` (`Board::busyText()`, the one place that sentence is made; `moth is starting…` while the window's own start of the service is under way). A value typed into either table while moth is busy is refused the same way, in the line. A row of the results list is written or kept with its address, kind and `all` (see row writes); the value cell being typed in is not replaced by the list's own reads. The game menu looks in one bottle at a time, since looking can start wine there and the core does one thing at a time: the line says `looking in <bottle>…` meanwhile, then the core's text when nothing is running there, and a submenu opened in the meantime says `looking in <bottle> first…` and looks once that is back, if it is still open. After a launch from the menu the window looks for the program every two seconds and attaches when it is listed; the wait ends once the game bar shows it attached, and after 90 seconds the line says `<name> did not show up in <bottle> after 90 seconds. see [home]/launch.log, or pick it once it is running.` A `kept` read that fails puts the core's error in the kept panel, where `nothing kept yet` goes, until a read works.

The window has a terminal on the right of the panels (`TerminalView`, libvterm for the screen, a pty for the shell), with a strip over it that shows the terminal's title and a `quiet` checkbox (the same switch as `moth quiet`; it shows what the board's `status` says). The terminal starts once, when the window is first shown, in the user's home folder: the user's shell (`SHELL`, else `/bin/zsh`) as `$SHELL -l -i -c '<command>\nexec "$SHELL" -l -i'`, so when the command ends the same terminal is a plain shell. `<command>` is `MOTH_TERMINAL` when that is set (a shell command line; empty means no command, a plain shell) and otherwise `'<absolute path of MOTH_BIN>' agent`, so the window starts Claude Code on this moth session by itself. The shell's environment is the window's, with `MOTH_HOME` and `MOTH_BIN` set, moth's own folder first on `PATH`, `TERM=xterm-256color`, no `MOTH_ACTOR` and nothing that belongs to the terminal or Claude Code session that launched the window (`terminalEnv`). `MainWindow::setTerminal(false)`, before showing, leaves the window with panels only (the tests that drive the panels do this). A test that lets the terminal start sets `SHELL=/bin/sh` and a temporary `HOME` first, so the owner's shell start-up files and agent are never run.

To try it away from your own session, give it a home of its own: `MOTH_HOME=$(mktemp -d /tmp/moth-XXXXXX) MOTH_BIN=$PWD/bin/moth bin/moth-app`. With `QT_QPA_PLATFORM=offscreen` it runs with no window on the screen. Close it, then `moth stop` with the same `MOTH_HOME`.

The code is in `app/src`: `CoreClient` (requests, starting the service, the feed), `Board` (what every panel reads: the game, the hunt, whether a request is running and whose, the line; and the way panels send requests), `MainWindow` (a column of panels in a splitter, and the line under it). The tests in `app/test` run offscreen against `FakeCore`, a `QLocalServer` in a temporary home under `/tmp` that answers as the service does, feed included. The home is made with a short template, `/tmp/moth-app-XXXXXX`, because a socket path may be about 104 bytes at most and `QTemporaryDir`'s default place is longer than that allows. `Rig` in `fake_core.hpp` sets up a fake, a client and a board; `FakeMoth` stands in for the `moth` program and notes each run; `FakeCore::feedRequests(false)` lets a test send a request's events itself, `FakeCore::refuseWatch` makes the fake refuse the feed, and `FakeCore::closeGame(name)` makes the next unrecorded `status` find the game closed and record it, as the daemon does. `MainWindow::setPolling(false)` keeps the one-second poll off for tests that count requests. A new test is `app/test/<name>.cpp` plus its name in `MOTH_APP_TESTS` in `app/CMakeLists.txt`; a new source file is one line in `moth_window`. `app/test/it_app.cpp` is not one of these tests: it drives the real window against the real service, for scenarios 33 to 36 in a bottle (below).

## engine speed

    make bench-native   # builds build/native/moth_bench and runs it

It prints four lines over a seeded 256 MiB fake memory. Each figure is the best of three rounds, and GB means 2^30 bytes.

- `scan: <x> s/GB, narrow: <y> ms`: a first scan and one narrow, using the twelve groups a search for the whole number 100 makes.
- `dense narrow: <a> s/GB on 1 worker, <b> s/GB on <n> workers`: a `same` step over every aligned 4-byte place, which keeps them all and stores their values again.
- `snapshot: <c> s/GB, first same step: <d> s/GB on <n> workers`: a snapshot with the six groups a snapshot hunt carries, then a first `same` step over them.
- `51M u8 values gained: <e> s/GB from a snapshot, <f> s/GB from a scan`: a step that leaves a 1-byte group with about 51 million places, which then take their values, once after a snapshot and once after a scan.

`build/native/moth_bench <workers>` tries another worker count for the first line. The default is 0 (auto), which is what the helper uses.

The figures are only a relative guide. Here, reading memory is a memcpy, so it measures the engine's own comparison work on Apple Silicon. The real helper is x86_64 code running under Rosetta inside wine. It reads memory through wine on one thread (`make bench`, below, measures the whole of it). Scanning reads on one thread and compares on the workers, so comparisons overlap the reads.

Measured on 2026-11-11 on an Apple M5 (10 cores), where auto means 8 workers:

| engine | scan | narrow |
| --- | --- | --- |
| auto (8 workers) | 0.28 to 0.30 s/GB | 13 ms |
| 1 worker | 1.54 s/GB | 13 ms |
| before parallel scanning (task 4) | 3.41 s/GB | 19.6 ms |

For a closer look at the real case, the same program was cross-compiled once with mingw-w64 (x86_64, `-O3 -static`) and run through CrossOver's wine, so under Rosetta. It gave 0.48 s/GB with auto workers, 2.37 s/GB with one, and a 34 ms narrow. There is no make target for this.

## end to end in a bottle

    make test-integration   # every scenario, one line each; exits 1 if any fails
    make bench              # scenario 10 alone: the real helper's scan speed

Both build moth and the helper first; `make test-integration` builds the window too (`make app`, so it needs qtbase), for scenarios 33 to 36 and 39 and 40. Then they run `core/integration/it_main.exe` (its own dune executable, not part of `dune test`). It launches the stand-in game (`bin/moth-target.exe`, or `bin/moth-target32.exe`) in the bottle `MOTH_TEST_BOTTLE` (default `uhmm`, a scratch bottle) with `WINE`, and drives `bin/moth ... --json` against it, checking each reply with what the game reports over its control port. Each scenario gets a fresh game. Everything runs under a new `MOTH_HOME` in `/tmp`; afterwards the daemon is stopped (which ends the helper) and the games are closed, whether the scenarios passed or not. The home is removed when everything passed and kept for its logs (`core.log`, `helper.log`, `target.log`, `launch.log`, `it_app.log`) when something failed. `it_main.exe [--bin <dir>] [-v] [scenario numbers]` runs a few scenarios by hand; `-v` shows each moth command and what it printed.

Scenario 12 (anti-cheat names) is not run in a bottle: it prints `skip`, and the daemon's unit tests cover it with a fake helper.

Scenarios 31 to 40 cover what the window relies on, the window itself, and the agent:

- 31, the feed: a second client watches over the socket while `moth find 3` runs. It hears find's `busy` line, then its event, whose `seq` is `moth log`'s newest. After a `status` sent with `record: false` it hears nothing for a second.
- 32, launch: `moth launch --bottle <test bottle> <bin>/moth-target.exe <port>`. The game connects back to the harness just as it does when the harness starts it (`Target_ctl.adopt` listens first, hands the port to the launch, then accepts). `moth games` lists it, `moth attach` finds it by name, and once told to quit it must leave the bottle's process list.
- 33, the window: `build/app/it_app edit`. The window types 9 over the row at `points`' address, keeps it as `points`, and the game then has 9.
- 34, the list follows: `build/app/it_app follow`. When the window prints `listed`, the harness sets `points` to 4 in the game and runs `moth next 4` (60 seconds at most). The window's list must read itself again and show 4 at that address, with nothing clicked.
- 35, two hands on rows: `build/app/it_app follow` again. When the window prints `listed`, the harness waits two seconds (the window has polled), runs `moth results --near <points' address>` and checks that row 1 is at that address, waits two seconds more (the window has polled again), and runs `moth set 1 4`: it must say it set #1, the game must have 4 in `points`, and the window's row there must read 4. Before the window's unrecorded reads stopped replacing the listing the command line's row numbers come from, this write was refused (`no result #1`) or landed elsewhere.
- 36, the game goes away: `build/app/it_app gone`. When the window prints `listed`, the harness tells the game to quit. The window must say the core's words for a closed game (`not attached. moth-target.exe closed.`, or `the game closed. attach again once it's running.` when a list's read found it first), list and keep nothing, show `no game attached`, and have its search box disabled; a find from the search bar must be refused with `not attached. run: moth attach ...`. The harness then checks that no `set`, `keep` or `undo` was logged meanwhile.

- 37, an agent's hand: `MOTH_ACTOR=agent moth find 3` is recorded with actor `agent` (`moth log`), a `moth next 3` with no `MOTH_ACTOR` with actor `user`, and `MOTH_ACTOR=robot moth status` exits 2 with `MOTH_ACTOR must be user or agent`.
- 38, wait (run in a home with a space in its name, `/tmp/moth it <pid>`, as 39 is): a session folder named for the harness's own pid, and `moth wait --session` on it, started by the harness. The person's `find 3` and `next 4`, half a second apart, end it with exit 2 inside 6 seconds, its stderr the heading and those two steps in order. A second waiter is first shown to be watching (after `moth quiet on` its cursor file says `quiet` at that event's seq), then keeps running 3 seconds after the agent's own `next 5` (`MOTH_ACTOR=agent`), and after `moth quiet on` and a person's `next 5` (its cursor must reach that step's seq, so it read it and did not tell it); after `moth quiet off` the person's `find 3` ends it with exit 2 and that step alone. Every waiter is killed at the end and must be gone.
- 39, the agent in the window: `build/app/it_app term` with `MOTH_CLAUDE` at `stub_agent.exe`, `SHELL=/bin/sh` and `HOME` a folder with a space in its name (under the harness's home). The window's terminal runs `moth agent`, which runs the stand-in, and `it_app` waits for `stub agent up`, attaches, types 3 and Return, and prints `clicked`. Within 10 seconds (the note is bundled for 1.5) `$MOTH_HOME/stub-notes` holds a note with `find 3`, and `stub-args` has `--settings` and a settings file under `$MOTH_HOME/agent/`. The harness then tells `it_app` to tick `quiet`; `status --json` says `"quiet":true`, and a person's `moth next 4` adds nothing to `stub-notes` in 4 seconds, while the stand-in is alive and a `moth wait` is under it (so the silence is the switch, not a dead agent). `it_app` then unticks `quiet` (`loud`), a person's `find 3` must produce a new note with that step alone, and `status` says quiet is off. Before that the harness requires `stub-runs` to hold two lines (the hook armed again after the first note), and `stub-env` to hold `MOTH_ACTOR=agent`, `MOTH_HOME=<the home>` and a `PATH` that starts with moth's folder. Then `it_app` types `bye` and Return (the stand-in ends, the terminal is a shell), waits for a prompt ending in `$`, types `moth status` and waits for `attached to`, and closes the window. `it_app` must exit 0, and every process that was below it (the shell, `moth agent`, the stand-in, the hook's shell, `moth wait`) must be gone.
- 40, no agent: the same with `MOTH_CLAUDE=/nonexistent`. `it_app` waits for `claude code is not installed` on the terminal instead of `stub agent up`, the find from the search bar still fills the results list, the shell prompt follows (`moth status` shows `attached to`), the window closes and nothing is left.

`stub_agent.exe` (`core/integration/stub_agent.ml`) is the stand-in for Claude Code: an OCaml program, since it reads the Stop hook's command out of the JSON settings file named after `--settings`. It writes its arguments to `$MOTH_HOME/stub-args`, one per line (a long argument as its first line only), and the settings file's `env` entries to `$MOTH_HOME/stub-env` (`KEY=VALUE` lines). It runs the hook's command with `/bin/sh -c` in a process group of its own, stdin `/dev/null`, stderr to a file, and exactly the settings' `env` entries plus `HOME` as its environment, as Claude Code applies the settings; each start adds a line to `$MOTH_HOME/stub-runs`. It prints `stub agent up` after the first start. Each time the command exits 2 it appends what it wrote to `$MOTH_HOME/stub-notes` and runs it again; on any other exit it stops running it. It ends when its stdin ends or it reads a line `bye`, and first kills the command's process group, so no `moth wait` is left (the waiter also ends by itself once the stand-in's pid is gone).

`it_app <edit|follow|gone> <bottle> <exe name> <number> <0xaddr> <new number>` builds the real `MainWindow`, `Board` and `CoreClient` offscreen, on the `MOTH_HOME` and `MOTH_BIN` in its environment (it won't run without both, so it never touches the default home). It attaches from the game bar, types the number and Return, finds the whole number at the address in the results list (reading more pages as needed, up to the 20,000 rows the list holds), selects it and prints `listed`. `edit` then opens the row's value cell in the table's own editor, types the new number and commits it with Return; the model writes the row with its address and kind. Once the write's event has come back and the list's check after it has been answered, `edit` checks that the list was not read again from the start and the row is still selected; it then keeps the row and waits for the kept table to show it, and for the check after the keep, and looks again. `follow` changes nothing and waits up to 30 seconds for an event, the list read again after it, and the new number at the address. `gone` changes nothing and waits up to 30 seconds for the game to be gone (36). `<new number>` is not used by `gone`. `it_app` prints one line per step (`-v` shows them), waits on each step with a deadline instead of sleeping, and prints `ok` at the end. A step that does not come true in time prints what it waited for, with the window's line, and exits 1. It ends by itself after three minutes whatever happens, and the harness kills it after four. Its stderr (Qt's own notes) goes to `it_app.log` in the home.

`it_app term <bottle> <exe name> <number> <text>` builds the window with its terminal on. It waits up to 60 seconds for `<text>` on the terminal's screen (any row, any case) and prints `terminal`, then attaches, finds `<number>` as above (no row is picked) and prints `clicked`. It then reads commands from its stdin, a line at a time: `quiet` ticks the `quiet` box and waits for the board to say so (prints `quiet`); `bye` types `bye` and Return into the terminal and then does what `shell` does; `loud` unticks the box the same way (prints `loud`); `shell` waits for a row ending in `$`, types `moth status` and Return, waits for `attached to` on the screen, and prints `shell`. After `bye` or `shell`, or at the end of stdin, it closes the window and prints `ok`. The harness runs it with `MOTH_CLAUDE`, `SHELL` and `HOME` set as scenarios 39 and 40 say, after starting the service itself (the window's own `HOME` is not the one CrossOver is found under), and checks by pid that nothing it started is left.
